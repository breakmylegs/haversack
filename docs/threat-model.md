# Threat model

Seeded from build prompt section 18 in slice 1 and extended every slice. Each entry has a mitigation or an accepted risk signed off by the owner before v1.0.0.

Status values: **planned** (mitigation designed, not built yet), **partial** (some of it built), **in place** (built and tested), **accepted** (risk accepted by the owner).

| ID | Threat | Mitigation | Status | Since |
|---|---|---|---|---|
| T1 | Token theft from disk | Mode 0600 token files, no logging, minimal scopes | in place (slice 6): `onedrive-token.json` written 0600; scopes `Files.ReadWrite.AppFolder offline_access` only, so a stolen token reaches only `Apps/Keepsake`; tokens and codes are redacted from logs (tested in `tests/test_app_cloud.py`); diagnostics exports never read the token file | 1 |
| T2 | Device code phishing | Flows start only from a user action and show the app name and expected domain | in place (slice 6): sign-in starts only from the Settings button; the verification page must be HTTPS on `microsoft.com` or `live.com`; the screen tells the user to check for `microsoft.com` and the name Keepsake | 1 |
| T3 | Malicious or wrong manifest paths | Root confinement, traversal rejection, preview before first sync | in place (slice 4): `resolve.to_logical` rejects unknown placeholders, `..`, `.`, absolute paths and drive letters; `resolve.scan` keeps every match inside its root after `realpath` and never follows symlinked folders; `resolve.safe_base` refuses over-broad `base` roots; the Games page previews files before any sync. Tests in `tests/test_resolve.py` (symlink cases run on device) | 1 |
| T4 | Zip slip during restore | Validate every entry before extraction | in place (slice 5): `snapshot._check_zip` requires every entry to be listed in validated metadata, a regular file, unencrypted, of the stated size and below a 1000:1 compression ratio; extraction joins inside its base with traversal checks and verifies each SHA-256. Tests with hand-crafted hostile zips in `tests/test_snapshot.py` | 1 |
| T5 | Cloud tampering or corruption | Hash verification of blobs and metadata. Encryption is a later option | partial (slice 5): metadata is validated (paths, kinds, `contentHash` recomputed against the file list); blobs are checked against `blobSha256` and per-file hashes before any restore; uploads are verified by the hash the store reports, or by re-download. Metadata itself is unsigned; an attacker with write access to the cloud folder could publish a consistent but malicious snapshot, limited by root confinement (T3, T8). Encryption remains out of scope for v1 | 1 |
| T6 | A game left frozen | Watchdog, `finally` blocks, resume on start | in place, used by the slice 8 launch gate (release in `finally`, tested with a forced failure and a timeout); originally for the slice 1 freeze test: `freeze.Freezer` persists PIDs before stopping, fails closed if it cannot persist, runs a 30 second watchdog thread independent of asyncio, keeps an in-memory copy if the state file is corrupt, and `KeepsakeApp.start` resumes leftovers. Tested in `tests/test_freeze.py` and `tests/test_app.py` | 1 |
| T7 | The wrong process frozen | Environment matching, user ownership, ancestry checks | in place for the freeze test: `procs.find_game_processes` matches `STEAM_COMPAT_DATA_PATH`, `SteamGameId` or `SteamAppId`, filters by UID, never selects the plugin or its ancestors; resume checks process start time so a reused PID is never signalled | 1 |
| T8 | Writes outside the allowlist | Central path validation used by every write | in place (slice 5): restore resolves every target, staging and backup path with `safepath.join_within` against its logical root before writing, re-checks parents before each move, and stages beside the save folder only; settings and store writes go through `safepath` too | 1 |
| T9 | Secrets or personal data in logs or diagnostics | Redaction tests | in place: `redact.redact` on every log record and on the diagnostics export; non-stock usernames hidden; tests in `tests/test_redact_log.py` and `tests/test_diagnostics.py` | 1 |
| T10 | Malicious update via compromised repository or release | Protected tags, SHA-256 checks, signature verification. **Changed by ADR-0004:** no CI, so releases are built locally from a deterministic zip and the minisign signature with a key held only by the owner becomes the main control; anyone can rebuild a tag and compare hashes | partial: `main` protected and `v*` tags immutable (ADR-0005), Actions disabled. Slice 2: `scripts/release.py` builds deterministic zips and signs `SHA256SUMS` when a minisign key is set; the updater requires a `SHA256SUMS` entry and Decky checks the zip against it. Slice 12 (ADR-0023): pure-Python Ed25519 and minisign verification in the updater, tested against RFC 8032's vectors; once a public key is pinned in `release_key.py`, an update without a valid `SHA256SUMS.minisig` is refused. **ADR-0036:** the verifier is proven against a real minisign signature; `release.py` signs with the laptop's sealed key, checks the signature with the plugin's verifier against the pinned key, and refuses to publish unsigned once a key is pinned. **Owner action:** run `scripts/signing.py setup`, then the key is pinned by pull request; releases before that are unsigned (accepted until then) | 1 |
| T11 | Personal data committed to the public repository | Synthetic fixtures, `.gitignore`, pre-commit secret scan | in place: `scripts/secret_scan.py` (plain in-repo script, no third-party scanner), `.githooks/pre-commit`, `pnpm run check`, optional local denylist, `.gitignore` for settings, tokens and diagnostics | 1 |
| T12 | GitHub API rate limits | Caching and quiet failure | in place: at most one automatic check a day, ETag `If-None-Match`, 403 and 429 keep the cache and report quietly, unauthenticated requests only (`keepsake.update`, tests in `tests/test_update.py`) | 1 |
| T13 | Two devices racing | Create-only writes and fork detection | in place: create-only on both stores, tested with racing writers in the shared store contract; OneDrive uses upload sessions with `conflictBehavior: fail`; slice 7 detects forks after every push and at every launch, and a push racing a pull is a simulator scenario | 1 |
| T14 | Clock skew | Hashes and parents decide | in place (slice 7): the decision table compares content hashes and parent links only; the two-device simulator runs one device three days behind | 1 |
| T15 | A registry merge corrupting a prefix | Backup, key-level scope, re-parse validation | in place (slice 11, ADR-0022): only manifest-listed keys of opted-in games; the merged text must re-parse, keep every other key byte for byte and match the snapshot exactly; foreign keys in a fragment refused; original copied first; written beside and atomically renamed, then read back; nothing written if Wine changed the file meanwhile; never while the game runs. Fault-injection tests at every write step in `tests/test_registry.py` | 1 |
